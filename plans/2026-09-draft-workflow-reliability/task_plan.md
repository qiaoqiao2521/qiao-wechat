- 编写日期：2026-09-07。

## 1. 目标

将已有「Markdown 或 HTML → 本地预览 → 图片/封面 → 微信草稿箱」整理成可安装、可核验、可恢复、可交接的最小产品闭环。
优先消除失败不可追踪、重复草稿、安装缺资源与排版支持边界不清；建立能跨会话接手的项目文档。

## 2. 背景与证据

- 项目已有 API、CLI、HTML 草稿工具页、主题画廊和测试，并不是从零开发。
- 根目录 `task_plan.md / progress.md / findings.md` 仍停留在 `wx-content-mesh-python → qiao-wechat` rename 任务；缺少 SpecMesh 长期入口。
- 当前包元数据 0.3.0；配置保留 WCM_ 前缀，默认 `draft_only`。
- HTML 入站有独立 prepare 路径并复用草稿提交，不应被 Markdown 产品思路覆盖。
- `PublishService` 设置失败状态后可能抛异常；外层 rollback 使失败记录是否持久化成为首要核验项。
- 素材唯一键不等于草稿幂等，当前 `create_wechat_draft` 路径会调用 `add_draft`，尚未见文章请求去重契约。
- OPS 记录的 2026-04-28 账号可创建草稿、手机预览返回 48001。当前权限未复验。
- `pyproject.toml` 显式包列表、外部图形转换、硬编码默认目录需要做干净安装验证。

详细事实、来源和不确定性见 [findings.md](findings.md)。

## 3. 使用者与核心场景

| 场景 | 输入 | 期望输出 | 失败时用户应知道 |
|---|---|---|---|
| S1 内容作者 | 已完成创作的 Markdown、封面、账号、主题 | 本地预览与可检查的微信草稿 | 哪个段落/图片/账号步骤失败，是否已提交 |
| S2 外部排版工具 | 已渲染 HTML 字符串/文件、素材根目录 | 保留排版意图的草稿 | 发生了哪些兼容转换；缺失资源来自哪里 |
| S3 操作者 | 文章 ID 或一次操作标识 | 当前阶段、已生成预览、草稿标识、下一步 | 是否可重试，还是结果未知需先核对 |
| S4 下一位维护者 | 新终端与仓库 | 通过索引恢复项目和任务上下文 | 哪些事实已验证、哪些只是历史记录/计划 |

## 4. 范围与非目标

本轮包含：连续性文档接入、旧命名收尾核验、发行制品、双入口兼容、排版/素材边界、操作结果持久化、重复请求语义、必要的小界面反馈与验收。

本轮不包含：新增选题系统、扩展科研 skills、通用图像站、复杂账户平台、全新前端框架、多租户 SaaS、Redis/Celery 迁移、自动绕过账号权限、真实公开发布。
已有能力保持兼容；「本轮不扩展」不等于删除已有源码。

## 6. 设计约束与建议契约

### 6.1 提交身份与版本

建议使用稳定操作键，将 account、source identity、content revision 和 action 区分。content revision 应涵盖正文、封面、作者、摘要及会影响最终输出的主题/选项；计算规则先写测试和说明。
同一请求键对应不同输入应返回冲突，不悄悄覆盖；内容修订或显式「另建草稿」产生新操作。
保存 render/input 摘要、已成功素材映射、微信 media_id 与阶段，避免依赖进程内字典。
具体字段名、表结构及 API 传参由阶段 2 设计后确定，此文不声称已有 `idempotency_key` 接口。

### 6.2 事务与远端副作用

先复现外层 rollback 造成的记录丢失，再选择独立 attempt 事务或等效持久化方案。
必须明确准备、调用、响应持久化三个边界；不要在数据库长期写锁内等待全部远端请求。
本地锁/唯一约束只能抑制本地重复，并不能消除「远端成功但响应丢失」。对该窗口保留 unknown/reconcile 语义（命名待定），先查远端可用证据或由操作者核对，之后再显式重试。
不能宣称实现微信远端 exactly-once，也不能将补偿动作简化为删除所有草稿。

### 6.3 内容与资源

Markdown 保留主题渲染；HTML 只做约定的兼容整理和素材替换。避免「统一外观」覆盖上游已完成的排版。
明确哪些图形需要预先导出、哪些可本机转换、哪些使用外部渲染；不可用时返回可执行提示，不能只保留原始源码当作成功。
内容仓路径、文件归档、主题导入边界需保留。现有 HTTP 文件入口仅在受信任部署边界内使用；开放远程访问是后续独立需求。
